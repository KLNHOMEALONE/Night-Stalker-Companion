## Почему наблюдаемо только 6007 (главная рабочая гипотеза)
Статика из `seg0` предсказала это ровно: обработчик `6019` читает из `g_state`
через резолвер `0x801e6c24` **всего два** поля — литералами `0xa1`(161) и
`0xa6`(166). А `state_index` команды `6007` — **ровно 161**. Значит
`6007 ↔ DistanceUnit` подтверждено и статикой, и живьём.
Остальные поля JSON (`Velocity/BulletWt/BulletBC/Altitude/Temperature/ScopeHt/
ZeroRange/Sharp/Color/BallisticData/DistanceSwitch`) берутся не из `g_state`, а из
локальной структуры солвера (`lw $a0, 0x60/0x68/0x6c/0x74/0x7c/0x84/0x8c/0x90/0x94($fp)`),
то есть из **снимка**. Отсюда: записи остальных `600x` могут менять `g_state`
незримо — наблюдаемость требует триггера обновления снимка.

## Что НЕ подтверждено и что делать в следующем окне
1. **Что обновляет снимок.** Кандидаты: профиль (`BallisticData` — похоже

2. **Масштаб для вещественных полей.** `par=` разбирается как целое, а
   `BulletWt`/`BulletBC`/`ScopeHt` — `%.2f`/`%.3f`/`%.1f`. Возможно, нужно

3. **Диапазон.** В этом окне во все слоты шло `par=7`; для `Velocity=7` и

# ОФЛАЙН-ПАС 21.11 (после окна записи): почему `600x` — не калькулятор

## Что проверено
1. **В таблице команд нет диапазонов и enum.** Запись — ровно 5 слов:
   `{cmd, 0, handler, 0, state_index}`. У всего кластера `600x` обработчик один —
   `0x801f0904`, то есть это **тупой** `g_state[state_index] = par`. Косвенно
   подтверждено живьём: `DistanceUnit` (enum 0/1) принял `7`. Значит проверок
   значений на канале нет вовсе.
2. **Следовательно `state_index` ≠ поле JSON.** Единственное реальное
   совпадение — `161`/`6007`/`DistanceUnit`. Остальные `600x` пишут настройки
   меню прибора, а не калькулятор, и `ACCEPTED_BUT_IGNORED` для них — не
   поломка, а «пишет туда, где `6019` не смотрит».
3. **Именовать `g_state[idx]` статикой нечем.** Вызовов резолвера `0x801e6c24`
   с литералом почти нет: `idx=161` — 9 мест, `idx=3` — 2, `idx=155` — 1,
   у `165/159/156/89/162/171/38/66/166` — ноль. Остальные читают динамическим
   индексом, ярлыков рядом нет.
4. **Профиль калькулятора — один объект, и у него ТРИ читателя.** Порядок полей
   совпадает везде: `DistanceSwitch, DistanceUnit, BallisticData, Velocity,
   BulletWt, BulletBC, Altitude, Temperature, ScopeHt, ZeroRange, Sharp, Color`.
   Читатели: HTTP `6019` (`0x801f1ff0`), второй JSON-сборщик (`~0x801f0340`),
   и DCT-текст (`0x801ee880..0x801ef340`, ключи `DistanceUnit=` … `Color=`).
   Рядом (`0x801ef32c`) — сериализатор прицельной марки (`GroupId= Style= PosX=
   PosY= Color= Distance=`, это поля `6009`).
5. **Все DCT-текстовые блоки — сериализаторы, не сеттеры.** Внутри цепочки
   append/itoa (`0x80020e70`, `0x80020bb4`, `0x80021b2c`), ни одного `strcmp`.
   Четыре строки `DCT_*` (`SetBallisticData`, `SetReticleData`,
   `WifiApp_SendCmdStatus`, `WifiApp_SendOtherStatus`) не имеют ни `lui`-ссылок,
   ни указателей в данных — то есть публично виден только **push-статус в
   приложение**, а имя сеттера в `seg0` не адресуется вообще.
6. `seg1` — отдельный модуль: ноль ссылок в строковую область `seg0`
   (`0x80400000..0x80420000`) и ни одного `lui` с `imm` `0x8040x`. Значит
   сеттер нельзя «додумать» из `seg1`, и база `seg1` для этой задачи не нужна.
7. `3034` — не дамп настроек (`<Value>0</Value>`), дополнительного канала
   чтения нет: свидетели по-прежнему только `6019` и `6009`.

## Вывод (важно, чтобы не долбить дальше)
Среди 88 HTTP-команд **нет записи профиля калькулятора** — там только чтение
(`6019`/`6009`) и записи меню (`600x` → `g_state`). Управлять `Velocity` и
когда через HTTP, скорее всего, нечем. Два реальных пути:
- **A. Перватвить запросы штатного приложения** при смене одного поля (Win, см.
   `notes/WINDOWS.md`, `tools/win61_capture.py`, `tools/sniffly_run2.txt`) и
   повторить их. Это ground truth быстрее любой реверс-инженерии: заодно
   вскроется, почему «значения не применяются» в самом приложении.
- **B. Зондировать сокет с проверке через `6019`.** Главная помеха сокета —
   «команды есть, ответов нет» — больше не помеха: свидетель существует, это

# ВТОРОЙ КАНАЛ ЗАПИСИ: `POST /` со `status=` (найдено 21.11, очень важно)

Причина, по которой мы две недели не находили записью калькулятора: **она не в
таблице команд.** В захватах штатного приложения (`02_api/capture/sprint-*/streams/`)
есть запросы вида
```
POST / HTTP/1.1
Content-Type: application/json
Content-Length: 35

{"status": "set_time", "value": ""}
```
и он же в форме `status=set_time&value=`. Ответ — обычный конверт
`<Cmd>3027</Cmd><Status>0</Status>`.

Что это значит:
1. **`3027` нет в нашей 88-элементной таблице** (в таблице есть 3026 и 3028/3029,
   а 3027 — нет). Значит `POST /` обслуживает отдельный диспетчер, и табличный
   фаззер его никогда не касался. Весь наш вывод «писать нечем» относится только
   к GET `custom=1&cmd=`.
2. Имена статусов — строки того же вида, что в бинаре приложения: в
   `01_ghidra/App_bin` (это Flutter-приложение PardVision2, 9.3 МБ, лежит у нас)
   есть `set_time`, `set_date`, **`set_ballistic`** @`0x7a1e30`,
   **`set_mem_ballistic`** @`0x6c1e50`, `set_reticle`, `set_group_name`,
   `set_ssid`, `set_passphrase`, плюс `ballistic_data`, `ballisticMode`,
   `ballistic_model`, `BallisticData`. То есть **DONE в калькуляторе — это
   `POST /` со `status=set_ballistic`** (сохранение в память прибора — вероятно
   `set_mem_ballistic`).
3. Тело приложение собирает из кусков: в бинаре лежат отдельные строки
   `"status":"` @`0x6e7560` и `value"`, цельного шаблона нет.
4. **На стороне прошивки этих имён нет** (`seg0`/`seg1`: ноль строк `set_time`,
   `set_ballistic`, `application/json`). Значит обработчик живёт в отдельном
   веб-модуле на флэше, которого нет в нашей выгрузке сегментов — угадать формат
   `value` по дизассемблеру нельзя, его надо видеть.

## Что делать
Снять одной операцией: дамп трафика приложения в момент нажатия DONE, затем
повторить запрос и проверить через `6019`. Формат `value` — единственное,
чего нам не хватает. Средство: `pymobiledevice3 pcap --userspace` (телефон по
USB, Mac остаётся дома в Wi-Fi, поэтому ассистент не отваливается), разбор —
`02_api/pcap_dump_streams.py` (pcapng-читатель дописан 21.11). Имена статусов
для сверки после захвата брать из списка выше.

|---|---|---|---|---|
| старая (`Z2QAM6wbRYNg94nhAAADA+gAAOpgBA==`) | 864x480 | право 8 | **848x480** | High 5.1, 4:2:0, 8 бит |

Контроль правдоподобия: `864` кодированных колонок минус `2×8` при обрезке =

**не** заявляет: разбирать VUI в этом файле сознательно не стали (та же яма, в
какую упал `parse_sps.py`), а `b=AS:2000` в SDP — это битрейт, а не fps.

## 6. Что отсюда следует для цели проекта

Баллистический профиль **не читается ни одним найденным каналом, кроме `6019`,
и не пишется ни одним найденным способом**. При этом `6019` между съёмками
менялся сам (`Velocity` 285→788, `BulletWt` 3.00→11.30, `Temperature` 20→5):
значит значения кто-то пишет, и писать их можно. Два оставшихся пути:

1. **Увидеть настоящий запрос приложения** (единственный оставшийся ground
   truth). Все прежние захваты сделаны в момент, когда калькулятор не открывали:
   в них есть только `set_time`/`set_date`. Требуется окно, в котором телефон и
   Mac сидят на AP одновременно (тогда работает или MITM, или ручной iOS-прокси
   на Mac) — сначала дешёвая проверка, что AP допускает двух клиентов со статикой.
2. **Спросить пользователя**, как именно менялись значения: кнопками прицела или
   приложением. Если кнопками — канал записи баллистики по Wi-Fi, вероятно, не
   существует вовсе, и цель «заводить данные в штатный калькулятор с телефона»
   недостижима на этой прошивке; это надо узнать раньше, чем писать клиент.

## ЗАХВАТ ЖИВОГО ПРИЛОЖЕНИЯ 22.11 15:33 — найден настоящий формат записи

`02_api/capture/app-live-261122-153307/traffic.pcap` (60 запросов, снято пассивным
`tcpdump` во время переключения марки в PardVision2 на Маке).

**Запись идёт в URL, не телом.** Марка:

```
GET /?custom=1&cmd=6001&par=0&GroupId=1&Style=2
GET /?custom=1&cmd=6001&par=0&GroupId=1&Color=1
GET /?custom=1&cmd=6001&par=0&GroupId=1&PosX=-1
GET /?custom=1&cmd=6001&par=0&GroupId=1&PosY=1
```

то есть транспорт GET, `par=0` константой (в марке; предположительно индекс
профиля), далее по одному настоящему имени поля на запрос. Чтение марки —
соседний `cmd=6009`. Литерал `6001` в бинарнике приложения лежит вплотную к
строке `ReticleModel`, что подтверждает принадлежность команды.

Строковые аргументы идут через `str=`:

```
GET /?custom=1&cmd=3005&str=2026-11-22      дата
GET /?custom=1&cmd=3006&str=15:33:38        время
GET /?custom=1&cmd=3031&str=all             (список, значение all)
```

Из этого следует, почему 46 форм `POST`-тела из `post_status.py` ничего не
дали: мы ломились телом туда, где всё лежит в query-строке, а `POST /` прицел
и не думал разбирать (он всегда отвечает `<Cmd>3027</Cmd><Status>0</Status>`).

Команда записи профиля калькулятора по-прежнему не видна: в macOS-сборке
приложения экрана баллистического калькулятора нет (пользователь не нашёл),
а в AOT-таблице строк id не читается. Рабочая гипотеза — соседний id рядом с
6019 (`6016`..`6021`, все отвечают `Status 0`) и те же имена полей, что отдаёт
6019: `Velocity`, `BulletWt`, `BulletBC`, `Altitude`, `Temperature`, `ScopeHt`,
`ZeroRange`, `DistanceSwitch`, `DistanceUnit`, `BallisticData`. Проверять по
одному полю со свидетелем 6019 и обязательным восстановлением,
`tools/probe_write.py` (по умолчанию `--id 6018 --field Velocity`, есть
`--dry-run`; POST, чужие поля и чужие id этим инструментом отправлены быть не
могут).

## КОМАНДА ЗАПИСИ ПРОФИЛЯ НАЙДЕНА И ПОДТВЕРЖДЕНА (22.11, `probe-window-261122-154937`)

```
GET /?custom=1&cmd=6018&par=0&Velocity=286     -> <Cmd>6018</Cmd><Status>0</Status>
cmd=6019 до:      "BallisticData":1, "Velocity":285
cmd=6019 после:   "BallisticData":0, "Velocity":286     # записалось
после отката:      "Velocity":285                        # вернулось
```

Значит пишущая команда профиля калькулятора - `6018`, сосед чтения `6019`,
формат ровно как у марки: `par=0` и по одному настоящему имени поля. Тот же
шаблон, что показал захват марки (`cmd=6001&par=0&Style=2`).

**Побочный эффект, обязателен к учёту в клиенте:** любая запись поля профиля
сбрасывает `BallisticData` с 1 на 0, и обратно он сам не возвращается. При
написании профиля это чинится тем же транспортом (`cmd=6018&par=0&BallisticData=1`),
но только если писать его после остальных полей, иначе новый сброс сотрёт его
снова. `tools/probe_write.py --keep` - режим «записать, а не нащупать»: пишет и
НЕ откатывает; без него зонд всегда возвращает baseline.

Зонд остановился сам после первого же кандидата именно из-за этого флага
(`!!! cmd=6018 оставил изменения`), что и было задумано.
