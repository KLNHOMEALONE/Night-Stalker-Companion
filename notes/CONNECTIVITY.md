# Как дать мне доступ к прицелу, не потеряв интернет

## Суть конфликта
У Mac один Wi-Fi радиомодуль (`en0`). Пока он в домашней сети — есть интернет и я.
Встанет на точку доступа прицела (`Pard_*`, шлюз `192.168.1.254`) — интернет и ИИ пропадут.

USB-кабелем не решить: прицел в `ioreg`/`system_profiler` как устройство **не виден**
(`00_recon/usb_before.txt` — только USB-хаб и логитечная мышь). У PardVision2 нет ни
одной строки USB-протокола; `wifi_iot` + `NSLocalNetworkUsageDescription`
= управление именно по Wi-Fi. Кабель у PARD — зарядка, в лучшем случае MSC-диск.

Поэтому: нужен **второй путь в интернет**, либо **одноразовый офлайн-захват**.

## Вариант A — iPhone как интернет по USB (быстрый, рекомендую)
1. iPhone кабелем в Mac → Настройки → Режим модема: **вкл** (разрешить USB).
2. Mac получит интернет через `bridge0`/`appleusb` — **Wi-Fi освобождается**.
3. Подключиться к сети прицела `Pard_*` вручную.
4. Провести зонд:
   ```
   cd ~/Projects/PARD_API/02_api
   python3 probe_device.py
   ```
5. Проверить, что интернет есть: `curl -s -m 5 https://10.84.159.1 >/dev/null; echo $?`
   (или просто открыть любой сайт — Wi-Fi уже не должен быть шлюзом).

Плюс: я остаюсь онлайн и могу рулить процессом в реальном времени и сразу копать
найденное. Это лучший вариант.

### ⚠️ ПРОВЕРЕНО В ЖИВУЮ — вариант A НЕ РАБОТАЕТ на этой машине
Пройдено по шагам: iPhone воткнут и спарен (UDID виден), «Режим модема» включён,
`en9` («iPhone USB USB») поднимался в `172.20.10.3`, дефолт шёл через `172.20.10.1`,
интернет отвечал `HTTP 200` за 45 мс. Но как только Wi-Fi включается (в любую сеть —
модемную, домашнюю, прицела), `en9` переходит в `status: inactive`: **iOS перестаёт
отдавать USB-тэтеринг, пока у Mac поднят Wi-Fi**. Проверено дважды, с перетыком кабеля.
Дополнительно: macOS авто-джойнит сохранённые сети (поймал `iPhone` и домашний Xiaomi на
`192.168.31.1`), поэтому «просто включить Wi-Fi» неконтролируемо.
Вердикт: для сценария «радио на прицел + интернет по USB» нужен **второй радиомодуль**
(USB Wi-Fi донгл) либо шлюз (вариант C).

## Вариант B — Android как мост
Телефон в сети прицела + USB в Mac:
```
adb shell                              # на телефоне есть toybox nc
printf 'GET / HTTP/1.0\r\n\r\n' | nc 192.168.1.254 80
```
Через `adb forward`/Termux(`sshd`) поднимается `ssh -L 8080:192.168.1.254:80`,
и я получаю устройство через туннель, не трогая Wi-Fi Mac.
Минус: возни больше, HTTP через `nc` неудобен для длинных ответов.

## Вариант C — Raspberry Pi / второй Linux как шлюз (лучше для глубокой работы)
Pijoined точку прицела, в Mac смотрит USB-gadget-.ethernet. Я получаю:
- маршрутизированный доступ к `192.168.1.254` через отдельный интерфейс Pi,
- полный `tcpdump` всего трафика (главный приз — **порт TCP-сокета `DCT_Socket_Cmd=5005`**
  и реальный RTSP URL, которые в статике не видны, потому что это числа в машинном коде).
Это единственный способ снять протокол целиком, включая передачу файлов.

## Вариант D — вообще без интернета: офлайн-захват (работает всегда)
Если терять связь не хочется совсем:
1. Вручную подключиться к Wi-Fi прицела (интернет и я на это время отключатся).
2. Запустить зонд — он работает **без интернета и без меня**:
   ```
   cd ~/Projects/PARD_API/02_api
   python3 probe_device.py
   ```
   ~100 запросов, всё складывается в `capture/<timestamp>/`.
3. Переключиться обратно на домашнюю сеть, вернуть меня.
4. Я разбираю дампы:
   ```
   zip -r capture.tgz capture/ && # прислать/указать путь
   ```
Хронометраж: 2–4 минуты офлайна. Риск нулевой, зонд ничего не отправляет наружу
(и не может — интернета нет).

Важно: зонд **только читает**. Он не шлёт `set_*` команды, не трогает Wi-Fi настройки
прицела и не запускает апгрейд прошивки — `/?custom=1&cmd=<N>` запрашивается через GET
без параметров подтверждения, а POST на `/upload` не выполняется.

## Что давит на вариант A/D в первую очередь
1. `query_cmd_list` → полный самоотчёт устройства о командах (снимает вопрос о числах `cmd=`)
2. список файлов с SD + их пути (`/mnt/<card>/Movie`)
3. порт TCP-сокета и формат пакетов `Function=0/1/2` + MD5
4. рабочий RTSP URL live view
5. точный вид ответа на `get_ballistic` / `set_mem_ballistic`

## Вариант E (лучший онлайн) — приложение на iPhone + шлюз
Так как сборка не запускается на Mac, приложение надо запускать на телефоне, а Mac должен
видеть его трафик. Для этого прицел и оба клиента должны быть в одном L2:
прицел → (Wi-Fi) → Raspberry Pi / OpenWrt-роутер → (ethernet/свой AP) → Mac и телефон.
Плюсы: я остаюсь онлайн, `tcpdump` на мосту видит **всё**, включая настоящий протокол
приложения (порт файлсокета, RTSP, `set_mem_ballistic`). Минус: нужен Pi или роутер.

## Вариант F (лучший) — iPhone крутит приложение, Mac снимает по USB через RVI
Ключевая мысль, которая решает весь конфликт «прицел vs интернет»:
**айфону интернет для работы с прицелом не нужен вообще**, а его трафик можно снять
с самого телефона по кабелю — `rvictl` (Apple Remote Virtual Interface) создаёт на Mac
виртуальный `rvi0`, зеркалирующий пакеты устройства. Mac в это время сидит на своём
Wi-Fi/роутере, то есть **я остаюсь онлайн**.

```
iPhone ──Wi-Fi──> прицел 192.168.1.254     (телефон без интернета)
   │
   └──USB──> Mac: rvi0 ──tcpdump──> pcap      (Mac с интернетом)
```

Инструмент: `03_usb/iphone_rvi_capture.sh`, распаковка `02_api/pcap_dump_streams.py`.
Так как `NSAppTransportSecurity → NSAllowsArbitraryLoads`, весь JSON летит открытым
текстом — pcap читается напрямую.

**Цена:** полный Xcode (в `rvictl` из Command Line Tools его нет), а он требует
macOS 26.6 при текущих 26.5.1 → сначала апдейт macOS до 26.7.3 либо xip с
developer.apple.com. Плюс Developer Mode на iPhone и «Trust This Computer».
