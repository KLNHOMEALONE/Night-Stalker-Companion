# Прошивка PARD Night Stalker 4K — что за файлы и что с них читается

Файлы принёс пользователь 19.11 ~00:15 в `pard/` (до этого их в проекте не было).

| файл | размер | что это (по факту, не по имени) |
|---|---|---|
| `pard/FWPDNS4.bin` | 4 337 908 (0x4230f4) | образ главному SoC **Novatek NT96660** (в заголовке строка `NT96660`); контейнер **BCL1**, два сегмента |
| `pard/LDPDDS37.bin` | 32 768 | код маленького MCU: начинается с ARM/Thumb-2 (`bl`), всего 170 строк — прошивка периферийной платы (дисплей/дальномер/балстика) |

Инструмент разбора: `tools/bcl_probe.py` (`python3 ../tools/bcl_probe.py FWPDNS4.bin`).

## Контейнер BCL1 (разобрано по байтам)

Магическое число `BCL1` два раза: `0x0` и `0x301a2c`. Заголовки **big-endian** —
это видно по полям размеров: для сегмента 0 поле `00 30 19 f4` = `0x3019F4`
ровно равно расстоянию до следующего заголовка (`0x301a2c`), для сегмента 1
`00 12 16 b7` = `0x1216B7` равно остатку файла (`0x1216c8`). Первое поле пары —
размер **до** упаковки (`0xB0AB54` ≈ 11.5 МБ и `0x1D7B0C`), то есть сегменты
упакованы, но не целиком (см. ниже).

Внутри нет заголовков `ELF`/`cramfs`/`squashfs`/`uImage`/`jffs2`/`UBI`. Есть 17
вхождений `1f 8b` и 10 вхождений признака `lzma-alone` — упакованные части
лежат кусками, а не одной файловой системой.

## Главное: HTTP-приложение лежит внутри **не упакованным**

Строки видны напрямую, а значит рядом должен быть и ARM-код (NT96660 — это
Cortex-A7, **ARMv7 32-bit LE**, в Ghidra `AARCHLE:ARMv7:A32`):

```
0x230706  '<?xml v'  ' ="1.0" encoding="UTF-8" ?>'
0x230739  '<Cmd>%d</'                      ← шаблон ответа, тот что мы видим по проводу
0x23078c  'custom='
0x230980  '1&cmd=%d&par'                    ← У КОМАНД ЕСТЬ ПАРАМЕТР par=
0x230bfd  'S:8192</'   0x230c11 '8/xxx.mov' ← шаблоны PhotoLiveViewLink/MovieLiveViewLink
0x2307bf  'mimeType'   0x230835 '<LIST>'    ← отдача файлов
0x2308a1  'SSID' 0x2308f0 '<Auth_t' 0x230908 '5<RSSI>%d dBm</'  ← поиск сетей
0x2309cc  'LkInfo(FST_INFO_DISK_SIZE)'      ← файловая система/накопитель
0x2307ef  '{"mfr":"%s","type...","p2p_uuid":""}' 0x23081c 'CarDV'  ← P2P/облако
```

Отладочные строки диспетчера (по ним находится код обработчика):

```
0x405ccf  'parsecmd: cmd='        0x40170f  'dhfs_fp cmd = %'
0x40185a  ', -p 8192 -s '         0x40b130  'hfs/1.00.'
0x4a1ea   'X: CMD=0x%x,Sts'       0x72873   'dCmd=%s'
0x229a2d  'GenCustom'             0x40b026  'getCustomD'
0x2a80cb  'xHfsNvt_SendIPC'  0x2a7fcc 'ipc_cmd='  0x2a80ff 'HFSNVT_SEM_ID'
```

## Что это меняет в плане

1. **`par=` — аргумент команды.** В переборе мы подавали только `cmd=`;
   пустые `Status 0` у большинства id объяснимы именно этим. В
   `NEXT_SESSION.md` пункт 5 исправлен с догадочного `&value=1` на `&par=`.
2. **Задача «имя → число» решается отсюда**, а не из iOS-приложения (там связи
   нет вообще, `notes/RE_FINDINGS.md`). Здесь же: ARM-код + `switch(cmd)` +
   отладочные строки на каждую команду — то есть имена команд, если они есть в
   `printf`-форматах, и уж точно семантика каждой команды по тому, что она трогает.
3. **Только читаем.** Никакой прошивки на устройство: выигрыша ноль, риск
   (несовпадение образа/обрыв записи) реальный. Образ уже у нас на диске.

## Проверка «совпадает ли образ с тем, что сейчас в прицеле»

Негативный результат, чтобы никто не искал повторно: номер версии (`174998`,
`175020`) в `pard/FWPDNS4.bin` **не хранится как текст** — `grep` ни по самому
номеру, ни по маске `^17[0-9]{4}$` в `strings` не даёт ни одного совпадения.
Значит номер либо бинарная константа, либо собирается из даты сборки.

Что работает вместо этого: шаблоны ответов из образа совпадают с тем, что
прицел отдаёт по сети прямо сейчас — `8/xxx.mov` (0x230c11) и `S:8192</`
(0x230bfd) против `cmd=2019 → rtsp://…/xxx.mov`, `http://…:8192`. Плюс заголовок
сервера `hfs/1.00.` лежит в образе на 0x40b130 — его стоит сравнить с живым
`Server:` из ответа (в логах он уже есть). Точное равенство сборок этим НЕ
доказывается, но противоречий нет.

# ПРОВЕРКА 19.11 (второй заход): предыдущий план «вырезать сегмент и дать в Ghidra как ARM» — НЕРАБОЧИЙ

Инструменты этой проверки: `tools/fw_isa.py` (узоры по байтам), `tools/fw_isa_score.py`
(капотновская линейная цепочка), финальный и единственный валидный тест — ниже.

## 1. В `FWPDNS4.bin` НЕТ исполняемого кода вообще (никакого ISA)

Тест на «инструкциях-возвратах», которые почти не встречаются в случайных данных
(калибровка по `/dev/urandom` той же длины и по ASCII-потоку):

| маркер                  | FWPDNS4 (4.3 МБ) | LDPDDS37 (32 КБ) | urandom 4.3 МБ |
|-------------------------|------------------|------------------|----------------|
| Thumb `bx lr` = `70 47` | 31               | **0**            | ~66 (ожидание) |
| ARM `mov pc,lr`         | 0                | 0                | 0              |
| ARM `bx lr` (A32)       | 0                | 0                | 0              |
| ARM `ldmfd sp!,{…,pc}`  | 0                | 0                | 0              |
| MIPS `jr $ra` (`08 00 e0 03`) | 5 (разбросанно) | **5, все в 0x9d0..0xb9d** | 0 |

Вывод: в 4.3-МБ образе нет ни ARM, ни Thumb, ни MIPS-кода — 31 вхождение `bx lr`
это уровень шума. Значит «строки HTTP-приложения видны не упакованными» —
ошибочное чтение: это литеральные прогоны **упакованного** потока.

Почему вводило в заблуждение: 6.83 бит/байт в среднем по файлу и 17 вхождений
`1f 8b` при полном отсутствии энтропийных «провалов». Локальная читаемая ASCII —
это литералы LZ, а не открытые данные.

## 2. Метр «доля валидно декодируемых инструкций» для Thumb — мусор, не использовать

Закалибровано (16 валидных подряд, старт каждые 2 байта):

| данные                 | Thumb-2 |
|------------------------|---------|
| `/dev/urandom`         | 44 %    |
| **ASCII-текст**        | **100 %** |
| FWPDNS4 @0x405000      | 94 %    |

Thumb-2 покрывает почти всё ASCII-пространство, поэтому на данных с литеральными
ASCII-прогонами он даёт ~95 % вранья. Для MIPS тот же тест честный: urandom 0 %.
`tools/fw_isa_score.py` оставлен, но читать его выводы по Thumb нельзя.

## 3. `LDPDDS37.bin` — это НЕ прошивка периферии, а MIPS32 (LE) загрузчик, и он же парсер BCL1

- Код: `0x0440..0x0b80` (1856 Б) и `0x5340..0x7f00` (последний — в основном `nop`).
- Константы `lui`: `0x8FF0xxxx` ×12, `0x8FF1xxxx` ×10, `0x8000xxxx` ×7 → периферия
  на `0x8FF00000`, кэш-луп по `0x80000000..0x80004000`, `jr $t6` на `0x8FF08100`.
- Строки (`0x4ae4..0x5340`): `BCL1` (дата-островок в `0xb84` сразу за эпилогом
  функции `0xa80..0xb80`), `Multi-bin found...`, `Total N partition`, `FW96660T.BIN`,
  `compressed-dsp`, `LFullComp`, `addr_src:`, `file offset not word align!`,
  `MaxFwCodeSize =`, `No uITRON in EMB`, `Unsupport forma[t]`, `SPI NOR detected`,
  `Run WrBin`, `card open`, `WRKEY`, `linux`, `:u-boot`.
- Функция `0x0a80..0x0b80($a0=src,$a1=dst,$a2=длина)` — **вот он, алгоритм
  распаковки**: читает байт-значение, потом два цикла накопления 7-битных
  групп (`sll 7 / andi 0x7f / andi 0x80` = varint с продолжением по старшему
  биту), потом цикл-copy из `dst` по смещению `out - count`. Это LZSS-семейство
  с RLE и varint-длины, а не LZMA и не Huffman (литералы лежат открытым текстом).

Это объясняет и « escape-байты» `0x9d`/`0x9f`, которых я насчитал 8.6 % и 3 %
файла: у обоих взведен старший бит, за ними всегда идут `0x04..0x10`, т.е. это
continuation-байты varint, а не opcode'ы.

## 4. Что делать завтра (порядок)

1. Дописать дизассемблирование `0x0440..0x0b80` целиком и переписать его в C
   руками: это ~180 инструкций, из них 4 цикла. Особых загадок две:
   семантика заголовка (`BCL1` + `be/chk` + размер_до + размер_после) и откуда
   берётся dictionary/back-offset в `0xb20` (`subu $t3,$v0,$t3`, т.е. `dst + out - count`).
2. Проверить гипотезу адреса: у `j` в файле цели вне файла при любом базовом
   (244 штуки, 0..3 попадают). Похоже, что `0xa80..0xb80` — перекомпилированный
   фрагмент, разрываемый даталендами, а `j 0x…c2091` — мусор от выравнивания;
   разрешается только после чтения `0x0440..0x9d0` (там пролог/инициализация).
3. Реализовать декодер по-русски в `tools/bcl_decompress.py` (только stdlib),
   критерий успеха: `0xB0AB54` байт на сегменте 0 и `0x1D7B0C` на сегменте 1,
   после распаковки — плотные ASCII-строки без разрывов и `70 47`/`08 00 e0 03`
   в коде. Тогда `cmd=`-диспетчер ищется в Ghidra за один заход.
4. Только после пункта 3 возвращаться к Ghidra/REA по основному образу.

## 1. ИСПРАВЛЕНИЕ: прошивка — MIPS32 little-endian, не ARM

`NT96660 = Cortex-A7 / AARCHLE:ARMv7:A32` — **неверно**. Подсчёт инструкций-
возвратов в распакованных сегментах (`tools/fw_isa_now.py`):

| маркер             | seg1 (1.9 МБ) |
|-----------------------------------|
| MIPS `jr $ra`      | **6975, все 4-выровнены** |
| ARM `mov pc,lr`    | 0 |
| ARM `ldmfd sp,pc`  | 0 |
| Thumb `bx lr`      | 6 (шум) |

Согласуется с загрузчиком: `LDPDDS37.bin` — MIPS32-LE. Все адреса строк из
раздела «Главное: HTTP-приложение лежит внутри не упакованным» выше — это
смещения в **упакованном** файле, после распаковки они другие (см. п.4).

## 2. Формат BCL1: заголовок дочитан до поля

Шаблон, который загрузчик держит в `LDPDDS37.bin:0xb84`, дал размеры полей
(magic, дальше 16-битное, 16-битное `9`, два 32-битных big-endian):

```
+0x00 4  "BCL1"
+0x04 2  checksum/build (seg0 0x7b5c, seg1 0x331b; у шаблона 0x0000)
+0x06 2  format version = 9
+0x08 4  РАЗМЕР РАСПАКОВАННОГО  (seg0 0xB0AB54, seg1 0x1D7B0C)
+0x0C 4  РАЗМЕР УПАКОВАННОГО    (seg0 0x3019F4, seg1 0x1216B7)
+0x10 .  поток
```

Поле `+8` в прошлом разделе было подписано правильно, но путаница осталась:
пакованное поле совпадает с размером области до следующего заголовка, т.е.
`0x3019F4` — это пакованное, а `0xB0AB54` — распакованное.

## 3. Алгоритм распаковки (переписан из `LDPDDS37.bin:0xa80`, Ghidra без обрывов)

Декодер: `tools/bcl_decompress.py` (`bcl_decompress(src, comp_len, expect=...)`).
Поток **побайтовый**, выравнивание по байту (гипотеза битового varint не
понадобилась). `ref = src[0]`; байт, равный `ref`, литералом не кодируется:

```
b == ref:  следующий байт 0  -> выдать один ref, расход 2 байта
           иначе varint(length), varint(offset), копировать length байт
                  из dst[out-offset]; offset==length-вариант даёт RLE
b != ref:  выдать b
выход: next_input_index >= comp_len   (третий аргумент ограничивает ВХОД)
```

Важные детали, обе стоят сбитых часов:
- varint: 7 бит на байт, продолжение пока взведён **бит 7**, старшая группа
  первой; счётчик групп — в delay slot'е ветвания, а delay slot в MIPS
  выполняется всегда, поэтому счётчик равен числу байт, а не «на единицу меньше»;
- третий аргумент ограничивает **входной** индекс, поэтому на seg0 он даёт на 4
  байта больше объявленного размера: останавливаться надо по размеру вывода
  (`expect`), тогда оба сегмента бьют пик в пик.

**Критерий успеха из п.3 выполнен:** `0xB0AB54` и `0x1D7B0C` — оба ровно.

## 4. Что получили: строки по настоящим адресам, и `Ballistic` рядом с `cmd=`

`tools/bcl_extract.py pard/FWPDNS4.bin 01_ghidra/fw` -> `seg0.bin`, `seg1.bin`.

- **seg1** (0x1D7B0C) — один **raw RTOS-образ** MIPS: ни ELF, ни cramfs/squashfs/
  UBI/jffs2/uImage (`tools/fw_find_bins.py`). Там `parsecmd` @`0x198bb0`,
  `hfs/1.00.` @`0x1a3c60`, `getCustomD` @`0x1a3a6b` — то есть сам HTTP-сервер тут.
- **seg0** (0xB0AB54) — приложение. `custom=` @`0x408ec4`, `<Cmd>%d` @`0x408db3`,
  `1&cmd=%d&par` @`0x4091e7`, и **`Ballistic` @`0x408984`, `0x408c90`, `0x4099a7`** —
  те же окрестности, что и шаблоны ответов: прямой след к командам баллистики.

## 5. НЕ РЕШЕНО: база загрузки seg0/seg1

Без неё Ghidra не разворачивает xref'ы на строки. База самого `LDPDDS37.bin`
нашлась однозначно: **`0x0FF076DC`** (единственное значение, при котором оба `j`

Для сегментов прошивки три захода не дали ответа, дальше не долбить этим же:
- `tools/ldp_jbase.py`-подобный поиск по `j` — в raw-образе цели вне сегмента;
- `tools/fw_anchor_base.py` (указатель как 4-байтный литерал) — 0 совпадений:

# ПРОВЕРКА 21.11 (офлайн-окно): БАЗА seg0 = `0x80000000`, ТАБЛИЦА КОМАНД ИЗВЛЕЧЕНА

Инструменты: `tools/fw_find_base.py` (база), `tools/fw_cmd_table.py` (таблица);
дамп — `01_ghidra/fw/cmd_table.txt` и `cmd_table.json`. Прицел не нужен.

## 1. Почему п.5 «не решён» — ловушка в маске `lui`
`lui rt, imm` = opcode `0x0F`, `rs=0`, а `rt` занимает биты 20..16. Правильная
проверка — `(w & 0xFFE00000) == 0x3C000000`. Проверка `(w & 0xFFFF0000) ==
0x3C000000` дополнительно закрепляет `rt==0` и теряет почти все `lui`: на `seg0`
это **37 «найденных» вместо 69651**. Отсюда и «пересечения по трём якорям пусто».

## 2. База: `VMA = смещение в файле + 0x80000000` (сегмент не релоцирован)
Метод (`tools/fw_find_base.py`): `lui` по смещению `o` материалзует абсолютный
адрес, значит каждая пара `lui`+`lo` — голос за `base = адрес - o`. Ошибочный
критерий «указатель попадает на ASCII» здесь не годится: образ набит строками, и
ложная база `0x8fb50000` тоже набирает 21156 «строковых» попаданий. Решает
голосование `lui` + независимая проверка (указатели на строки и на прологи).
Доказательство — три независимых контроля:
- указатели из таблицы команд попадают ровно на пролог `addiu $sp,$sp,-n`
  (`0x801f0904 -> 27bdffb8`), 32/32;
- указатели enum-блоков попадают ровно на начало строк (`0x80409c10 = "OFF"`,
  `0x80409c14 = "3MIN"`, `0x804031e8 = "Color"`);
- счётчик попаданий: у `0x80000000` 2583 строки + 4016 прологов, у ближайшего
  конкурента (`0x7fff0000`) 2252 + 499.
**Ghidra: `MIPS:LE:32:default`, image base `0x80000000`, блок с `0x808d96d0` —
`data`.** Для `seg1` та же программа даёт кандидата `0x8faa0000` (2420 прологов),
но это ЕЩЁ НЕ ПРОВЕРЕНО — не сверяно ни с одной известной строкой.

## 3. Таблица команд (её искали два окна): VMA `0x808d96d0..0x808d9db0`
`seg0`, смещение `0x8d96d0`, **88 записей, шаг `0x14`**, найдена чисто как данные
по отпечатку id. Перед ней заголовок `1, 80, 443, 1` (`0x8d96c0`), после —
enum-блоки допустимых значений.

```c
struct cmd_entry {            /* шаг 0x14, значения уже АБСОЛЮТНЫЕ VMA */
    u32 cmd;                  /* то, что шлём как ?custom=1&cmd=<cmd>       */
    u32 byte_slot;            /* 0 или &g_flags[i] в структуре 0x8000e000    */
    u32 handler;              /* 0 или функция, форматирующая ответ          */
    u32 flags;                /* 0/1/4/8/16/32/64 (не всегда 0 — не фильтр!) */
    u32 state_index;          /* индекс в g_state[], 0 = ответа нет          */
};
```

Обвязка: инициализация `0x801f4c0c` (`lui $a0,0x808e; addiu $a0,-0x6930`) кладёт
адрес таблицы в глобальную `0x80d38044` через `0x80304f68`; читалка — `0x80304f8c`;
цикл снимания значений и сборки ответа — `0x801f0678`; резолвер значения
`0x801e6c24(id) = *(0x80b582f4 + (id+0x29)*4)`, то есть **`state_index` — индекс в
массиве настроек `g_state`**.

Сходится с живой съёмкой до байта: `6008` и `6020` в таблице **нет** → прибор и
отвечает `-256`; `6017` в таблице есть (`state_index=66`) → отвечает `-3`, а не
`-256`; записей `Status 0` в кластере ровно 18 (16 общей обработкой + `6009` +
`6019`).

## 4. ГЛАВНОЕ ПО ЦЕЛИ ПРОЕКТА: канал записи — `par=`, он разбирается в прошивке
Общий обработчик `0x801f0904` (у всех `6001-6007, 6010-6018, 6021`, а также
`1001`) доставал из запроса три имени: `custom=` (`0x801f0918`), `cmd=`
(`0x801f09c0`) и **`par=` — два раза, `0x801f0a34` и `0x801f0b58`**. Шаблоны
прошивки: `custom=1&cmd=%d&par=` @`0x4091e0` и `custom=1&cmd=3031&str=`
@`0x409414` (для `3031` строковый аргумент — `str=`).
Значит форма записи: **`GET /?custom=1&cmd=<600x>&par=<int>`**.

`6009` и `6019` — форматирующие читалки, `par=` не разбирают вообще:
- `6019` @`0x801f1ff0`: `{"DistanceSwitch":%d,"DistanceUnit":%d,"BallisticData":%d,"Velocity":%.0f,"BulletWt":%.2f,"BulletBC":%.3f,...` @`0x80408c68`;
- `6009` @`0x801f2158`: `{"GroupId":%d,"PosX":%d,"PosY":%d,"Style":%d,"Color":%d}` @`0x80408c2c`.

Отсюда модель цели: **читать композит через JSON (`6019`/`6009`), писать отдельное
поле через `cmd=<600x>&par=<v>`** — то есть «применяется сразу» штатно возможно,
и своей модели стрельбы по-прежнему не нужно.

## 5. Допустимые значения (enum-блоки сразу за таблицей, шаг 8: `char *; u32 idx`)
`0xFFFFFFFF` в поле `idx` — это числовой `0` и одновременно конец блока.
`OFF/3MIN/5MIN/10MIN` · `+2.0..-2.0` (шаг марки) · `OFF/ON` ×7 · `LOW/MED/HIGH` ·
`OFF/1MIN/10MIN/30MIN` · 17 языков `EN..BG` · `Color/Black And White/Yellow/Green/Red`
· `m/yds` · `6x/12x`. Полный список печатает `tools/fw_cmd_table.py`.

## 6. Что осталось открытым
1. **Какой `600x` какому полю JSON соответствует.** В таблице у `600x` только
   `state_index` (165, 159, 4, 156, 89, 161, 3, 155, 162, 171, 38, 66; у
   `6001/6014/6015/6018/6021` — 0). Поле `0xa1`(=161) встречается в обработчике
   `6019` литералом — значит `6007` и есть одно из полей калькулятора. Брать не
   угадыванием, а экспериментом: прочитал `6019` → записал `600x&par=` → снова
   прочитал `6019`, изменившееся поле и есть ответ.
2. Применяется ли запись сразу (то же окно).
3. База `seg1` — кандидат `0x8faa0000` не проверен.

# ПРОВЕРКА 21.11 (второй заход, тоже офлайн): статическую карту
## `cmd -> поле` снять не удалось, и вот почему (не долбить этим)

Что нашлось попутно и годится как опоры для будущего треиса:

- **Текстовый протокол DCT (сокет, не HTTP).** Рядом с JSON-шаблоном лежат
  ключи `BallisticData=` @`0x408984`, `Velocity=` @`0x408994`, `BulletWt=`
  @`0x4089a0`, `BulletBC=` @`0x4089ac` и `DCT_SetBallisticData` @`0x4099a0`.
  На них по очереди ссылается **одна функция, `0x801ee9b8..0x801ef290`** — блок
  на каждый ключ. Это второй (сокетный) путь к тем же полям, полезный, если
  HTTP-запись не применится: `tools/rw_probe.py --dct` бьёт именно туда.
- **JSON-шаблоны имеют по два места сборки.** Кроме обработчика `6019`
  (`0x801f1ff0`, шаблон `0x80408c68`) формат собирает ещё и `0x801f03e4`;
  то же для `6009`: `0x801f2158` и `0x801f04ec` (шаблон `0x80408c2c`).
  Вторая пара — похоже выкладка тех же данных в сокет/OSD, то есть тот самый
  треис «кто пишет в структуру» надо вести от неё.
- **Почему карта не берётся из данных.** Обработчик `6019` берёт значения НЕ из
  `g_state[]` напрямую, а из **локальной структуры**: `lw $a0, 0x60/0x68/0x6c/
  0x74/0x7c/0x84/0x8c/0x90/0x94($fp)`, каждое через `jal 0x800267a8` и только
  потом `sprintf` (`jal 0x8001ed9c`). Из `g_state` через резолвер
  `0x801e6c24` читаются лишь два поля, литералами `0xa6`(166) и `0xa1`(161).
  Значит `state_index -> поле` живёт в коде (конвертер из `g_state` в структуру
  калькулятора), а не в таблице.
- **Второй таблицы настроек нет.** Прогон по всему `seg0`: значения
  `state_index` (165, 159, 156, 155, 162, 171) вне таблицы команд больше нигде
  не собираются в осмысленный кластер — единственный «кластер» на `0x8cb72c`
  это совпадения по числу `0x59` (89 встречается 210 раз). Дескрипторов вида
  `{имя, индекс, min, max, список значений}` в образце нет.
- **Базу `seg1` проверить этим способом НЕЛЬЗЯ.** Тест «найти `lui`-пару,
  материалзующую адрес известной строки» даёт 0 попаданий вообще, ни для
  `0x8faa0000`, ни для любых других баз, включая `0x80000000` — то есть
  некорректен сам тест (строки `parsecmd:`/`custom`/` unknown cmd=%d` в `seg1`
  не адресуются парой `lui`+`lo` в пределах 4 слов), а не база неверна.
  Для `seg1` нужен другой способ: Ghidra с image base `0x8faa0000` и счётом
  загрузившихся функций, либо разбор `jal`-графa.

## Графика OSD и маски марок: что найдено и что отвергнуто (23.11)

### Найденное

Таблица имён ресурсов окна настройки марки, `01_ghidra/fw/seg0.bin`, участок
`0x402f58..0x40536c` (217 имён вида `UIMenuWnd*`):

```
UIMenuWndSetupReticle_{Option,X,Y,OnStyle,OnColor,OnSave,Tab,Warning}
UIMenuWndSetupReticle_StaticIcon_BG
UIMenuWndSetupReticle_Status_Reticle70X1H   70X1W   70X2H   70X2W
UIMenuWndSetupReticle_Status_Reticle50X1H   50X1W   50X2H   50X2W
UIMenuWndSetupReticle_Status_Reticle2
UIMenuWndSetupCursor_{X,Y,Tab}, _Static_Cursor
UIMenuWndWiFiMobileLinkOK_Static_Distance{1,2,3}, _Status_DistanceUnit,
UIMenuWndWiFiMobileLinkOK_Status_Reticle{50X1H,50X1W,50X2H,50X2W,70X1H}
```

Что это объясняет, и чего не объясняет:

- иконка текущей марки **зависит от кратности** (`70X` = 7.0x, `50X` = 5.0x) и
  имеет варианты `1H/1W/2H/2W` - восемь иконок плюс отдельная `Reticle2`. То есть
  «виды марок» в прошивке живут не одним списком из семи, а парами
  кратность-вариант;
- `Static_Distance{1,2,3}` и `Status_DistanceUnit` - три виджета дистанции и
  отдельный блок единиц: косвенно в пользу того, что `DistanceSwitch` связан с
  отображением дистанции, но маски дальномера здесь не названы;
- это **имена виджетов, а не растров**. Сами картинки в них не встроены.

Участок разреженных данных (кандидат в хранилище графики) - `0x440000..0x5b0000`,
1.4 МБ; отдельные острова в `0x5c0000..0x620000`, `0x660000..0x680000`,
`0x7b0000..0x7f0000`, `0x8f0000..0x990000`, `0x9c0000..0xad0000`. Карта по окнам
64 КБ строится `tools/fw_scan_images.py`.

### Отвергнуто пятью проверками (не повторять без нового знания)

1. Ранжирование блоков по энтропии: лучшие кандидаты - чистое заполнение.
2. Зеркальность по вертикали в 1bpp: ловит шахматный паттерн `0x55/0xAA` и
   шрифтовой атлас (в ASCII читается как ячейки `##..#####`, это текст).
3. То же с фильтром по периоду и пробегу штриха: остаются строки-таблицы,
   где полная строка `####...` зеркальна тривиально.
4. IoU по чернилам (фон больше не даёт очков): 39 кандидатов в участке графики,
   при просмотре - строки и таблицы, не фигуры.
5. Указатели в участок графики (`0x80440000..0x805c0000`), массивами по 3 и 7:
   **ноль попаданий** - ресурсы адресуются не абсолютными указателями, а
   относительными смещениями внутри своего пакета.
6. Поиск «заголовка каталога» перебором пар u32: то, что выглядело как каталог в
   `0x447eec`, оказалось восемью записями и непоследовательными размерами.

### Отсюда вывод и следующий шаг

Статистикой маска не находится, потому что неизвестны ни формат пикселя, ни
способ адресации - нужен загрузчик ресурсов UI. Детерминированный путь: в Ghidra
(проект `01_ghidra/PARD_MIPS.gpr`, образ `01_ghidra/fw/seg0.bin`, база `0x80000000`)
взять строку `UIMenuWndSetupReticle_StaticIcon_BG` (`0x4033d4`), найти
ссылающийся код, и по нему выйти на функцию получения ресурса по имени: там
станет понятны шаг записи и кодировка пикселей. После этого переписать
экстрактор, а не искать глазами.

Оценка шансов: средняя. Возможный итог реверса - маски оказываются примитивами,
которые OSD рисует линиями (у NT96660 есть аппаратный вывод линий), и тогда
готовых битмапов марок в образе нет вовсе. Дешёвая страховка - снимки с прицела:
`tools/fetch_photos.py` проверен, остаётся один кадр, чтобы узнать, попадает ли
марка в сохраняемый JPG.

### Поправка к предыдущему разделу: `50X`/`70X` — НЕ кратность

Прочтение `Reticle70X` = 7.0x было выдумкой: по словам владельца кратности здесь
8, 12, 16, 24 и 32. Рядом в той же таблице лежат
`UIMenuWndWiFiMobileLinkOK_Status_PIP{50X1,50X2,70X1,70X2}` - картинка-в-картинке
в 50% и 70%, поэтому `50X`/`70X` - это процент размера вставки, а не оптика.

Что установлено разбором дескрипторов (шаг записи ровно 0x60, база `0x8bc270`):

| поле | значение | смысл |
|---|---|---|
| +0x08 | 7 (у `Reticle2` - 9) | тип виджета |
| +0x0c | 0x808bc254 и т.д. | self/родитель |
| +0x10 | указатель на имя | строка из `0x4032..` |
| +0x14 | 0x104 | идентификатор класса |
| +0x24 | 0x80b56e1c, шаг 8 | **адрес за концом образа** (`0xB50E1C > 0xB0AB54`) - рантайм |

Вывод, экономящий чужое время: дескрипторы указывают в ОЗУ, а не в растры.
Связь «имя виджета -> картинка» строится в рантайме по имени, и ни в `seg0`,
ни в `seg1` открыто масок марок нет. Проверялось: `seg1` вообще не содержит
разреженных данных (это образ Wi-Fi-сопроцессора, RTL8192), других сегментов в
пакете нет - `0x3019f4 + 0x1216b7` равны размеру `FWPDNS4.bin`, то есть
сегмента ровно два и оба распакованы. Отдачу по hfs дают только `/PARD/Photo`,
`/PARD/Movie` и `/LDPDDS37.bin`.

Абсолютное число иконок марки: восемь (`{50,70}X{1,2}{H,W}`) плюс `Reticle2`.
Семь стилей марки этим не описываются - значит вендор в окне марки, скорее
всего, тоже показывает живое изображение, а не галерею иконок. Проверка дешевле
поиска битмапов: снять экран меню выбора марки на прицеле (один кадр) и заодно
три кадра с карты по `tools/fetch_photos.py`. Оси `1/2` и `H/W` остаются
неизвестными: варианты цвета, «контур/закраска» или разные дальномерные маски.
