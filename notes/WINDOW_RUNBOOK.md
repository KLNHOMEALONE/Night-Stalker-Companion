## ПРАВИЛА БЕЗОПАСНОСТИ (22.11, после инцидента — нарушать нельзя)

`GET /?custom=1&cmd=<N>` без аргумента **не является чтением**, если в ответе нет
тела: такие команды исполняются. Доказательство на живой карте — прицел сам снял
по файлу ровно в старт прогонов: `/PARD/Photo/PARD_20261121_002145.JPG` к старту
00:19 и `PARD_20261122_132858.JPG` к старту окна 13:28:54. Три слепых перебора
`cmd=1..8191`, сделанных раньше, исполняли неизвестные команды; версии прошивки
между съёмками менялись (175020 → 174998 → 174996 → 174993), и рядом лежат id
`3025`/`3026`, отдающие URL сервера обновлений и локального файла прошивки.

Политика, она вшита в `tools/window_readonly.sh`:

1. слепых переборов id — больше никогда;
2. отправляется только id, у которого уже наблюдалось **тело** ответа
   (`<Value>`/`<String>`/`<head>`): тело и есть признак чтения;
3. `3025`/`3026` запрещены даже с телом — они из потока обновления прошивки;
4. URL не должен содержать `del=`, `format`, `factory`, `reset`, `update`,
   `upgrade`, `erase`, `delete`, `reboot`, `poweroff` — проверка в коде, а не на слово;
5. удаление файла на этом device делается гетом `GET <файл>?del=1`, поэтому ни
   один повтор и ни один паук не имеет права брать из страниц прицела URL со
   знаком `?` (в `scope_webui_grab.py` этот фильтр уже есть, он и спас);
6. `tools/window_ballistic.sh` (POST-подбор и перебор) без `PARD_ALLOW_UNSAFE=1`
   не стартует и только подсказывает, чем его заменить.

Единственная разрешённая команда окна:

```
./tools/window_readonly.sh
```

## ОКНО 22.11 14:16 — read-only прогон, `02_api/capture/ro-261122-141653`

**Найдено то, чего не хватало: `cmd=3014` — пакетное чтение состояния.** Один
запрос возвращает 34 пары `<Cmd>NNNN</Cmd><Status>значение</Status>`, и `Status`
там — не код ошибки, а текущее значение:

```
1002=3   2016=0  2001=0  2002=5  2003=1  2004=0  2005=6  2020=50  2021=0
2022=8000 2023=0 2024=0  2006=0  2007=1  2008=1  2011=2  2012=0   3007=0
3008=0   3009=0  3028=0  3033=0  6002=1  6003=7  6004=7  6005=7   6006=7
6007=0   6010=7  6011=7  6012=0  6013=0  6016=0  6017=1
```

Практический смысл два. Первый: это официальный список того, что прицел знает, —
все 34 id и раньше отвечали в переборе, ни одного нового не всплыло, то есть
перебирать было нечего. Второй: значения «пустых» id теперь читаются одним
запросом, не исполняя их, — наш собственный клиент будет опрашивать меню так, а не
десятком запросов.

**Удаление содержимого карты — следствие прогона `window_ballistic.sh` в 13:28.**
Хронология по mtime артефактов, она же доказательство:

| время | что произошло |
|---|---|
| 13:28:59 | листинг `/PARD/Photo` ещё отдаёт 9 файлов — карта на месте и заполнена |
| 13:29:19…13:29:30 | 46 POST-запросов `status=set_ballistic`/`set_reticle` |
| 13:29:33…13:30:20 | **слепой перебор 641 неизвестного id** (`8990-9020`, `8192-8800`) |
| 14:16:54 | корень hfs пустой, `/PARD` → «Page Not found», `3017` даёт 98304 вместо ёмкости |

Между «карта полна» и «карта пуста» к прицелу обращался только этот прогон, и
`del=` для этого не требовалось: у id, отвечающих пустотой, эффект ровно такой же,
как у нажатия кнопки в меню прицела. Номера id, который это сделал, мы не
назовём: перебор сохранял id и статус, а не последствия. Вероятно оттуда же и
обнулившееся чтение версии (`cmd=1003` = 0 вместо 174993) — рядом лежат id потока
обновления.

Отсюда правила выше — они не «на всякий случай», а следствие: ни одного слопого
перебора, ни одной записи в неизвестный id, а перед любым окном SD-карта из
прицела вынимается физически, чтобы терять было нечего.

## Почему окно нельзя вести «вживую» (важно, не забыть)

`pi` работает на Mac и для каждого шага ходит в сеть моделей. AP прицела интернета
не даёт вовсе — значит на время подключения к `PARD_387acce83577` агент отваливается
окончательно, а не «терпит». Режим один (A). Пункт B ниже — чтобы не соблазняться:

**A. Автономно (как всегда).** Агент готовит прогон ДО, прогон сам пишет всё в
файлы, агент разбирает ПОСЛЕ возвращения в сеть. Свежие пробы пишут сырой лог
запрос/ответ на каждой операции (`--capture`), поэтому даже разорванное по
середине окно остаётся разбираемым:
```
cd ~/Projects/PARD_API
python3 tools/cmd_par_probe.py --capture 02_api/capture/cmd-par-probe-raw.jsonl
```
В конце печатается `CMD PAR PROBE DONE — switch back to your home Wi-Fi now.`
Только тогда и отключаться. Идентификация сборки (`3012`, `1003`) снимается сама,
в начале лога.

**B. Живой режим — НЕРАБОЧИЙ, проверено (не предлагать).** Идея была: интернет по
USB-tethering телефона либо Ethernet, Wi-Fi — к AP прицела. Она противоречит
опровергнутому пути №3 из `SESSION_STATE.md`: iOS перестаёт отдавать USB-tethering,
как только Wi-Fi включается (проверено дважды, с перетыком кабеля), а Ethernet-хаба
в хозяйстве нет. Владелец подтвердил 23.11: «вариант Б никогда работать не будет».
Значит режим всегда один — A.

## Приоритет №0: второй канал записи — `POST /` со `status=`

Найдено 21.11: штатное приложение пишет **не** через `GET custom=1&cmd=`.
В захватах есть `POST /` с телом `{"status": "set_time", "value": ""}` и его
form-близнец `status=set_time&value=`; ответ — `<Cmd>3027</Cmd><Status>0</Status>`.
Команды `3027` в 88-элементной таблице нет (есть 3026 и 3028), то есть это
отдельный диспетчер, и весь наш табличный фаззер его не касался. Имена статусов
лежат в `01_ghidra/App_bin` (Flutter-приложение PardVision2): `set_ballistic`
@`0x7a1e30`, `set_mem_ballistic` @`0x6c1e50`, `set_reticle`, `set_group_name`,
`set_recording_duration_s`. Кнопка DONE в калькуляторе — почти наверняка
`status=set_ballistic`.

**Чего мы НЕ знаем:** формы поля `value`. Ни `seg0`, ни `seg1` этих имён не
содержат — обработчик в другом модуле на флэше. И **кнопку как код найти не
удалось**: строки `DONE` в бинаре нет (подпись из локализации), имён класса/
обработчика экрана тоже (Dart AOT их вычищает; `BallisticScrollActivity`/
`BallisticSimulation` — это физика прокрутки из Flutter, а не калькулятор), а
`tools/dart_str_xref.py` на этих строках даёт `PTR none` при мусорном
`class_ptr` — заголовок посчитан по 8-байтовой раскладке, в билде, похоже,
сжатые указатели. Соседство `Done` с `ballistic` в таблице строк ничего не
доказывает. Вывод: форму либо видим, либо подбираем экспериментом.

## Приоритет: сокет-калькулятор с свидетелем `6019` (`tools/dct_probe.py`)

Профиль калькулятора не пишется ни одной из 88 HTTP-команд (доказано в
`notes/CMD_TABLE.md`, раздел «ОФЛАЙН-ПАС 21.11»). Канал — текстовый сокет. Что о
нём известно не из догадок, а из дампов и `seg0`:
- на `:443` лежит открытый текст: в `02_api/capture/api-20261118-215251/streams/`
  есть поток с литералом `DCT_Socket_Cmd` и с `DCT_Socket_Cmd=5005&Function=0`
  (TLS handshakes там нет — значит MITM для этого не нужен);
- ответов сокет не даёт **ни в одном из 37 потоков** — ровно поэтому он две
  недели считался бесполезным. Свидетель теперь снаружи: после каждой отправки
  перечитывается `6019`/`6009` по HTTP;
- имена полей берёт из прошивки: сериализаторы `0x801ee880+` выдают `Velocity=`,
  `BulletWt=`, `BulletBC=`, `Altitude=`, `Temperature=`, `ScopeHt=`, `ZeroRange=`,
  `Sharp=`, `Color=`, `DistanceUnit=`, `BallisticData=`; для марки — `GroupId=`,
  `Style=`, `PosX=`, `PosY=`, `Distance=`.

```
python3 tools/dct_probe.py --apply                       # ballistic, порты 443 8000
python3 tools/dct_probe.py --profile reticle --apply     #DCT_SetReticleData
python3 tools/dct_probe.py --apply --field Velocity      # одно поле, максимально
```
Без `--apply` зонд ничего не шлёт и печатает словарь форм. Значения для полей
берются из живого baseline и сдвигаются на **уместный** шаг (`BulletBC` на 0.01,
`Velocity` на 10), каждое изменение сразу возвращается полной профилем, а в
конце печатается сверка финального состояния с исходным. Проверено на моке:
применяющий сокет даёт `APPLIED` по всем 12 полям и `restore OK`, игнорирующий —
36× `NO_VISIBLE_EFFECT` и `final state == baseline`.

Если и сокет нем — значит профил вообще не пишется извне, и тогда остаётся
перватчивать запросы штатного приложения (`notes/WINDOWS.md`).

## Порядок в окне

1. Телефон — **вне** сети прицела (иначе единственный клиентский слот AP занят,
   Mac ассоциируется, но lease `192.168.1.x` не получит).
2. Подключиться к AP `PARD_387acce83577` вручную. Серая иконка с «!» — это норма.
3. Убедиться, что адрес есть: `ipconfig getifaddr en0` → `192.168.1.x`
   (если нет: `sudo ipconfig set en0 DHCP`).
4. Запустить и **не трогать**:

   ```
   ./03_usb/scope_api_sprint.sh
   ```

   `sudo -E` не нужен; root покупает только `session.pcap` (`PCAP=on`).
   Стадии: 1/7 запись+read-back+restore → 2/7 зонд `par=` на 3033-3120 →
   3/7 листинг файлов → 4/7 RTSP → 5/7 слушатели 443/8000/8192 →
   6/7 перебор id `4096-8191` (лимит `SWEEP_BUDGET`, по умолчанию 600 с,
   возобновляемый) → 7/7 стримы.
5. В конце напечатано `API SPRINT DONE — switch back to your home Wi-Fi now.`
   Вот тогда и отключаться.

Если прогон оборвался — ничего страшно: `probe_par.jsonl` пишется с `flush()` на
каждой записи, а перебор id возобновляется по ledger. Запустить ту же команду
повторно можно хоть в том же окне.

## Что само себя починит при смене прошивки

`ledger` больше не выбирается вручную: в начале окна читается `cmd=1003`
(версия) и `cmd=3012` (имя), и если оператор не задал `SWEEP_LEDGER` явно,
файл берётся по версии (`cmd_sweep-ledger-v<версия>.jsonl`; для известной
`174998` — существующий `cmd_sweep-ledger-NEWFW.jsonl`, чтобы не потерять
47 уже отвеченных id). Причина: resume пропускает уже отвеченные id, и два
снимка разных прошивок в одном файле делают дифф «до/после» невозможным.

Если прицел снова перепрошьют — просто запустить спринт ещё раз, версия в
начале окна напечатается, и ledger подставится другой.

## Приоритет №1 в следующем окне (10 минут, одна команда)

Прошивка дала канал записи (`notes/FIRMWARE.md`, «ПРОВЕРКА 21.11»): писать надо
тем же `custom=1&cmd=`, но с `par=`; читается всё теми же `6019`/`6009`. Поэтому
в окне, сразу после `nc -z 192.168.1.254 80`:

```
cd ~/Projects/PARD_API
python3 tools/cmd_par_probe.py --dry-run          # план, без сети
python3 tools/cmd_par_probe.py --settle 0.3       # 17 слотов, сам восстанавливает
```

Он делает `W(cmd,par) → R 6019 → R 6009 → восстановить → проверить` для каждого
`600x` и печатает `cmd → поле`. Решать на месте ни на что не надо; если
соединение рвётся на середине — `--cmds 6010,6011,...` остатком: состояние
прибора не портится, потому что каждый шаг с восстановлением.


Что проверено на моке (не на приборе): белый список запросов, разбор `Style` из
`cmd=6009`, остановка при расхождении перечитывания, откат к исходному стилю.
На моке же видно, что слоты `6010`-`6016` отвечают пустым `<Status>0</Status>` -
это то же самое, что мы видели на живом прицеле, поэтому живой результат будет
смысл читать по приложенной ниже легенде, а не по коду ответа.

Легенда результата:

| ответ слота | значение |
|---|---|
| `<Value>число</Value>` | слот читается, это число |
| `<String>{...}</String>` | слот отдаёт объект (как `6009`) |
| пустой `<Status>0</Status>` | слот не читается, только пишется |
| `<Status>-256</Status>` | слот есть в таблице прошивки, значения нет |
